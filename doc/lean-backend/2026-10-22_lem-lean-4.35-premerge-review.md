## Findings

### P2-1. The record under-describes the 4.35.0 behaviour the fix works around, and plan B is not told to look for the rest of it

- Where: record §3 (d) and §9; `doc/lean-backend/DESIGN.md:433-437`; comment at
  `src/lean_backend.ml:5670-5676`.
- Claim in the record: "4.35.0's code generator inlines the private nullary def into its use
  sites". Fix scoped to `lemLetRhs_*`; §6/§9 conclude the cerberus half is unaffected because it
  has no such site.
- Evidence (scratch package `.tmp/review-lem435/inl`, v4.35.0, the pin's own extern):
  ```
  p=(3,6) q=(9,12) r=(23,26) t=(17,20) u=(21,22)
  f 0=29 f 0=29 f 1=28
  ```
  `p` = mainline's private shape (reproduces the record's (3,6)); `q` = a PUBLIC nullary def,
  same module, destructured: re-evaluated per projection; `r` = public nullary def consumed from
  ANOTHER module: re-evaluated; `t` = consumed by `.1`/`.2` projections, no `let`: re-evaluated;
  `u` = the branch's `@[noinline]` shape: single evaluation; `f n := r.1 + n`, a FUNCTION
  consumer: the IR of `lp_inl_f` calls `tickPairImpl` directly, so the constant's body runs on
  every call of `f`. A pure closed constant (`tbl := (List.range 200000).map (· * 2)`) was NOT
  inlined (its consumer reads `lp_inl_tbl`, initialised once through a `lean_once_cell_t`).
- Judgement: privateness and the `lemLetRhs_` shape are incidental. The observed class is a
  nullary def whose body is small and cannot be extracted as a closed term (here: it mentions a
  `never_extract` constant); 4.35.0 inlines it into every consumer, functions included, and the
  consumer recomputes it per use. Within lem-lean the fix is sufficient for the one site the m7
  pin observes, and I found no other LemLib/suite site of that shape that a gate watches. But
  the same mechanism applies to (a) generated nullary defs whose body calls an
  `@[never_extract]` function (every generated function with a `fail` site gets that attribute,
  `src/lean_backend.ml:5919-5933`; Cerberus's generated tree has 9 such attributed defs and
  LemLib's `failwithI`/`fail` are never_extract), and (b) hand-written seams with nullary defs
  wrapping opaque/`implemented_by` externs (Cerberus's `unsafebaseio_allowlist.txt` classes).
  For pure-with-failure code the semantics are unchanged (the constant's own initialiser still
  runs at init, as `_init_lp_inl_r` shows), the cost is not; for an impure extern it is the m7
  semantics change again, outside the pin's reach.
- Fix: (1) reword §3 (d), DESIGN.md:433-437 and the emitter comment to the measured class
  ("a nullary def whose body is a small non-extractable call, private or not, inlined into every
  consumer including function bodies"); (2) add to §9 a plan-B task: census nullary defs in
  `generated/` and the seams whose body mentions a never_extract constant (grep `@[never_extract]`
  callees and the allowlist seams), and run the timing lane/ladder cost rows before and after
  the re-pin; (3) register the policy question (should the emitter mark every generated nullary
  def `@[noinline]`, or only never_extract-mentioning ones) as a TODO item needing a ruling —
  it is not this slice's change. No lem-lean code change required for merge.

## Verdict

**MERGEABLE WITH FIXES.** The code on the branch is sound and small: one attribute at one
emitter site that does exactly what the pin needs and nothing the kernel sees; a proof repair
that proves the same statement with standard axioms; exact deprecation swaps; a pin updated to
the toolchain's name without loosening. The fixes are not code: (P2-2) an explicit operator
ruling on the red `leantests` gate recorded before the ff, and (P2-1) the record/DESIGN
wording corrected to the measured 4.35.0 behaviour plus a plan-B instruction to census and
cost-measure the broader class in Cerberus's tree and seams. P3 items are doc hygiene.
