## 3. What 4.35.0 broke: the scoping table against what was found

Scoping §2 rows that concern lem-lean, and the outcome:

| Scoping row | Outcome |
|---|---|
| `toList_bal`: "`omega` no longer sees the `height` match unfolded (8 goals)" | Reproduced (8 `omega` errors at `LemLibPmapLaws.lean:129:16`) but the diagnosis was off: `omega` was not the failing step. See (a). |
| two new reserved words `monotonicity_by`, `recall` (+ `Erased`, `repeatM`) | Confirmed exactly: `scripts/lean_keyword_probe.sh` reported `MISSING … (2): monotonicity_by recall` in both lists (180 core keywords on 4.35.0, 178 on 4.32.2); the generator reported exactly `Erased repeatM` new. | "no generated change" | True for every input without a top-level multi-name destructuring let; the repair in (d) changes exactly those (§6). |

(a) `toList_bal` (`lean-lib/LemLibPmapLaws.lean`). On 4.35.0 `unfold bal`
leaves the two `let hl := height l; let hr := height r` binders at the head
of the goal as `have hl := …; have hr := …`, and `split` no longer splits
the outer `if hl > hr + 2` under them: it splits the inner `match l`/
`match r` and the inner `if height ll ≥ height lr` first, generalising the
discriminants, so the outer-`if` hypotheses never enter the context. The
`create` arms then reach the `exfalso; omega` alternative with nothing
contradictory in context (e.g. `h✝ : a✝.height ≥ a✝³.height ⊢ False`),
which is the "omega could not prove the goal" the scoping saw; the
companion warning `LemLibPmapLaws.lean:128:13: This simp argument is
unused: toList_create` says the same from the other side. Repair: `dsimp
only` right after `unfold bal` zeta-reduces the binders; the rest of the
proof is unchanged. Probed in scratch (`lake env lean`, 4.35.0): the
repaired theorem closes with axioms `[propext, Quot.sound]` and no
warning; the alternative `simp only [bal]` also closes. Not kernel-opaque
anywhere; no option raised.

(b) `#synth BEq UInt64` (`TestInstancePriorityCheck.lean:68`, leg 5 of the
BEq lattice). Verbatim from the suite's `lean-compile` on 4.35.0:

    error: TestInstancePriorityCheck.lean:68:0: ❌️ Docstring on `#guard_msgs` does not match generated message:

    - info: instBEqOfDecidableEq
    + info: instLinearOrderPackageUInt64✝.toBEq

Measured on both toolchains with one scratch file: on 4.35.0 `#synth BEq`
gives `instLinearOrderPackageUInt64✝.toBEq` at `UInt64` (`UInt8`, `UInt32`
likewise), `Int.instLinearOrderPackage.toBEq` at `Int`, and
`instBEqOfDecidableEq` at `Nat`, `String`, `Char`, `Bool`; `#synth
LawfulBEq UInt64` gives `Std.LawfulBEqOrd.lawfulBEq` (`Nat.instLawfulBEq`
at `Nat`). On 4.32.2 every one is `instBEqOfDecidableEq` and `LawfulBEq
UInt64` is `instLawfulBEq`. The property the leg protects — LemLib's
`[Eq0 a] : BEq a` (450) and comparator bridges (400) sit below core's
instance, so `==` at a base type is core's with `LawfulBEq` and the core
simp set — holds on 4.35.0: the winner is core's, lawful, and the test's
`LawfulBEq`, `simpa` and `rfl` legs (lines 69-75) passed unchanged. The
expectation text is updated to the 4.35.0 name; the check is not loosened
(it still fails if a bridge wins). DESIGN.md and the lattice note record
the 4.35.0 fact.

(c) Deprecations. `if_false`/`if_true` (7 sites, `LemLibPmapLaws.lean`) →
`ite_false`/`ite_true`; `if_neg` (2 sites, `TestFuelMonoExemplar.lean`) →

No `if_pos` site exists in the tree (grep); `ite_cond_eq_false` is also

(d) The m7 single-evaluation pin (`lean-tuple-once`). Verbatim:

    === m7 single-evaluation pin (tuple-let RHS runs once) ===
      FAIL (exit 1): draws: first=3 second=6
    single-evaluation FAILED: RHS did not run exactly once (got (3, 6), want (1, 2))

The generated module is unchanged from 4.32.2: one `private def
lemLetRhs_first_draw_second_draw : Nat × Nat := TupleLetTick.tickPair ()`
and two projection defs. The compiled IR
(`lean-test/.lake/build/ir/Test_tuple_let_once.c`) calls `tickPairImpl`
three times: in the private def's own initialiser and again inside each
projection — 4.35.0's code generator inlines the private nullary def into
its use sites, so the (hand-written, `never_extract, noinline`-armoured)
impure extern runs once per projection: (1, 2) at init that nobody reads,
then (3, 4) and (5, 6). Measured in a self-contained scratch package (the
pin's `TupleLetTick.lean` + the generated shape, no LemLib) on both
toolchains:

    4.35.0: Plain (3, 6) · @[noinline] (1, 2) · @[never_extract] (3, 6) · both (1, 2)
    4.32.2: Plain (1, 2) · @[noinline] (1, 2) · @[never_extract] (1, 2) · both (1, 2)

So `@[noinline]` on the shared RHS def restores the OCaml semantics (the
tuple is bound once) on 4.35.0 and is a no-op on 4.32.2; `never_extract`
alone does nothing here. The emitter now emits `@[noinline] private def
lemLetRhs_…` (`src/lean_backend.ml:5697`); DESIGN.md says so. This is the
one output change of the slice (§6). The pin itself is unchanged.
