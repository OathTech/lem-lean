3. **HIGH — Surface argument order does not specify the library callback order.** `design:9`, `design:15`. The missing representation contract is observable in a ubiquitous function. `library/list.lem:279` implements OCaml's `map` through `count_map`; its recursive tail is evaluated before `f hd`, and it switches to `map_tr` after the counter threshold. The OCaml `List.map` representation is commented out at line 298, whereas Lean uses `List.map` at line 301. Linking a fresh small probe against the current generated OCaml library produced:

   ```text
   Lem_list.map callback order: 3,2,1
   Lem_list.map first failure: 3
   ```

   The inputs were `[1;2;3]`; the second callback raised its input as the message. A conventional left-to-right monadic map would fail at `1`. Even a uniformly reversed adapter would miss the long-list `map_tr` transition. Thus a pure success-equivalent target representation plus an arrow-effect annotation is not enough to select its failure-aware replacement. Set/map traversal and comparison callbacks have the same general obligation. The note's expression-level right-to-left rule does not govern computations hidden inside such a representation.

   **Suggested fix:** make invocation order, conditional invocation and application stages part of the semantic obligations of `failure_rep`. Work out the `List.map` adapter against this actual OCaml implementation, including the transition, or identify a requested ruling if that behavior is to change. Add a small pair of differently failing callbacks and a threshold case to its evidence. Also spell out the existing strict partial-application exception for Boolean operators: `src/lean_backend.ml:7333` and `tests/comprehensive/lean-test/TestSupplyCheck.lean:61` show why an operator's name alone does not imply short-circuit evaluation.

4. **HIGH — The global-abort choice needs a concrete ND/state interface and a disposition of existing typed model stops.** `design:17`, `design:19`, `design:57`. Keeping construction failures outside ND is sound, but failures can also occur when a suspended state function is forced. Cerberus's `frontend/model/nondeterminism.lem:51` stores `st → action × st`; its bind forces both the old action and a continuation at lines 62–76. Structural arrow lifting naturally changes that field to `st → Except Failure (action' × st)`, which does not return a state on failure. The separate supply formula in the note retains supply state, but does not settle this model-state/trace question or the new `nd_bind`, `liftND` and runner types.

   Runner order needs its own rule. `cerberus-lean/ocaml_frontend/smt2.ml:75` explores NDnd siblings left-to-right while prepending their results; line 117 explicitly sequences NDbranch left before right. Translating the two recursive calls in the existing Lean `left ++ right` expression by the general right-to-left rule would select the wrong first abort. Outer failure also needs a policy for results/traces already accumulated before that abort.

   There is an existing boundary decision to reconcile: `cerberus-lean/lean_frontend/CerbFail.lean:16` implements intentional model stops as ND kills, and `CerbMem.lean:2542` uses one for an OCaml `failwith` arm. These are not ordinary modeled UB just because they are already typed. The note must distinguish preserving that accepted behavior from migrating it to a global abort; its current domain-error sentence does not identify these sites.

   **Suggested fix:** show translated ND data, bind/lift and exhaustive/single-trace runner signatures and representative equations. Give examples for a failure while constructing an action, a failure after a state update, and two differently failing siblings. State which state, trace and earlier results survive, and distinguish traversal order from returned-list order. Classify the existing C-TF1 model stops and typed fuel outcomes explicitly, with an operator ruling where their behavior changes. Price this as a core seam/API migration.
